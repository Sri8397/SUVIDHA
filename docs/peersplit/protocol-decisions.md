# PeerSplit protocol and implementation decisions

This log records decisions that constrain cryptography, identity, relay traffic, and backup compatibility. These are implementation choices, not a security certification.

Latest saved implementation/verification status: [30 October handoff](HANDOFF.md). Historical status paragraphs below may describe earlier gates; the handoff records which checks completed and which remain pending.

## ADR-001 — Use Marmot over MLS for encrypted group membership and messages

- **Status:** Selected; local identity creation, public-key copy, encrypted KeyPackage storage/publication, one-member group creation, manual relay sync, and an outbound invite UI are wired in code. The invite flow requires the recipient's published KeyPackage. KeyPackage publication returned success on the physical device, but a successful two-identity invitation/acceptance and interoperable replication remain unverified; revocation is unimplemented.
- **Why:** PeerSplit requires multi-member groups, invitations, authenticated membership changes, key epochs, and exclusion from future messages after removal. A custom shared AES key protocol would make membership authentication, rekey sequencing, history handling, and concurrency SUVIDHA's responsibility. NIP-17 is designed primarily around per-recipient wrapped messages and does not supply group administration or removal. Marmot combines Nostr identity/relays with MLS group key agreement and epoch changes.
- **Protocol:** Adopt Marmot over IETF MLS (RFC 9420), using the pinned library's group-creation API and the explicitly selected KeyPackage profile. Nostr identities use the protocol's secp256k1/Schnorr model. MLS owns group membership/key state and application-message protection; do not add a parallel custom AES group cipher. The current prototype passes `currentProfile = false` for KeyPackage publication; conformance to the library's newer current-profile factory is not claimed.
- **Pinned library:** `com.vitorpamplona.marmot:marmot-jvm:2.2.1` (MIT). Its API is being called for local MLS group creation and restore. The dependency currently requires compile SDK 37, so the project toolchain was raised to AGP 9.1.1 and API 37.0. The app's old public DSL/Kotlin plugin combination uses temporary AGP opt-outs; revisit those before AGP 10. The SDK group-state contract is implemented with Android Keystore AES-GCM storage, including durable sender-ratchet writes.
- **Relay transport:** Nostr WebSocket relay events are a transport and untrusted mailbox. Use at least two configured relays before treating sync as resilient. Relay timing, size, network address, and routing metadata remain observable; do not promise metadata privacy or “zero knowledge.”
- **Invite and removal rules:** Use Marmot/MLS KeyPackages, Welcome, Commit, and epoch transitions. A removed participant may retain plaintext and keys already received; the claim is only that future epochs exclude them. No invite payload should contain a raw long-lived group key.
- **Evidence and limits:** Marmot documents Android/Kotlin support and MIT licensing; MLS RFC 9420 defines epochs, membership changes, and group message protection. SUVIDHA's use of the JVM artifact and local group creation is not a claim of cross-client interoperability. The physical device published a KeyPackage successfully; encrypted bundle persistence, protocol transport-state recovery, local roster persistence, and sender-binding checks pass. Welcome ingestion now creates a Room group; KeyPackage bundles and pending commit state are included in backup payload v3. The actual two-identity relay exchange, network-failure scenarios, and removed-member epoch tests remain gates. UI copy must not promise production-grade end-to-end security.
- **References:** [Marmot protocol](https://github.com/marmot-protocol/marmot), [Marmot Kotlin implementation](https://github.com/vitorpamplona/marmot-kmp), [published Android artifact](https://central.sonatype.com/artifact/com.vitorpamplona.marmot/marmot-android), [RFC 9420](https://www.rfc-editor.org/rfc/rfc9420).

## ADR-002 — Manual backup uses an independent versioned encrypted file

- **Status:** Partially implemented; format and repository tests pass. Clean-install export/import with real Keystore/MLS state remains unverified.
- **Container:** A fixed binary header records format/KDF version, bounded PBKDF2-HMAC-SHA256 work factor, random salt, and random AES-GCM nonce. Authenticate the full header as GCM associated data. Reject unknown versions, excessive work factors, malformed sizes, wrong passphrases, truncated data, and modified ciphertext before parsing records.
- **Secret handling:** The user enters a recovery passphrase per export/import. Do not persist it. Clear mutable passphrase/key/plaintext buffers where practical. Do not log URI contents or secrets.
- **Restore:** Decode and validate a complete snapshot, show record counts, then replace Room rows inside one transaction. Identity and MLS blobs are protected by the passphrase envelope in the file and re-wrapped by Android Keystore on restore. App-private key/state files are staged/restored with rollback around the Room transaction; atomicity across SQLite and Android Keystore files is best-effort, not a single OS transaction. Retain a prior encrypted backup before restore.
- **Scope:** Manual SAF document export/import only. Payload v3 includes the Nostr identity secret, MLS group state/retained epochs/sender ratchets, the private KeyPackage bundle, encrypted transport obligations/gates/ingest markers, ledger outbox payloads, and pending Welcome deliveries. Payload v1/v2 remain readable with defaults. A fresh-install restore of this complete protocol state still requires a device verification gate. Google Drive is a separate planned adapter. Phone contacts and app preferences are not included.

## ADR-003 — Carry immutable ledger actions inside MLS application messages

- **Status:** Implemented; Room/migration/envelope checks pass. Live two-identity relay proof is in progress.
- **Contract:** `suvidha.shared-ledger`, version 1, contains a unique action ID, group ID, authenticated actor, causal parents, description, event time, and integer debt or settlement payload. The actor must match the MLS sender leaf. Expense creditors must equal the action author; only a creditor/debtor may settle the referenced debt. Amounts and balances are replayed locally rather than transmitted as authoritative absolute balances.
- **Outbound:** Build an unsigned inner rumor with the envelope as its text, then use `buildGroupMessage` for MLS protection. Store the domain event and exact encrypted outer event in one Room transaction before publishing. A relay ACK changes local status to “relay accepted”; it does not claim delivery to a peer. Manual retry republishes the same signed event.
- **Invitations:** `MarmotManager.addMember` returns a `WelcomeDelivery`; the caller must persist and publish its `giftWrapEvent` explicitly. SUVIDHA queues it separately from the financial ledger and retries it from Sync now. Always fetch Welcomes on a fresh install, process them before group messages, and persist joined group metadata/membership into Room.
- **Why the API distinction matters:** In the pinned library, `buildTextRumor` takes **text first**, followed by optional reply references. It does not take a group ID. `addMember` publishes the membership commit internally but returns the wrapped Welcome for caller delivery. Inspecting the actual published source caught both integration errors before the live-flow claim.
- **Source evidence:** [Pinned Marmot 2.2.1 source artifact](https://repo.maven.apache.org/maven2/com/vitorpamplona/marmot/marmot-jvm/2.2.1/marmot-jvm-2.2.1-sources.jar), `client/MarmotManager.kt` (`buildTextRumor`, `addMemberInvites`) and `MarmotWelcomeSender.kt` (`WelcomeDelivery`, `wrapWelcome`).
- **Background delivery:** WorkManager schedules a network-connected pass every 15 minutes, catch-up on app resume, and durable delivery after local changes or backup restore. Immediate requests coalesce, with at most one pending follow-up behind a running pass. UI polling awaits each pass, skips busy protocol operations, and pauses outside the resumed group screen. All service instances and backups share a process-wide protocol lock; database reset uses the same lock. Workers preserve cancellation, bound each pass to four minutes, and retry network failures or undelivered outbox items with exponential backoff for up to five attempts. Invalid remote events alone do not cause retries. Subsequent periodic passes remain scheduled after a failed run.
- **Limits:** Relay pagination/cursors are not implemented, and Android background scheduling does not guarantee instant delivery. A process interruption between a successful membership change and queuing its returned Welcome still needs a recovery/reinvite path; encrypted commit obligations alone do not contain the Welcome bytes. Concurrent membership changes, epoch forks, and revocation require dedicated verification before release.
