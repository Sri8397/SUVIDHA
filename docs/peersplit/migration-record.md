## Why explicit migrations are required

Room persists user data in SQLite. When the schema version changes, the app must transform the existing database into the new schema. A destructive fallback can drop and recreate tables when Room cannot find a migration; the app's pre-upgrade file copy is useful recovery insurance, but it does not preserve a user's in-place database or prove that the app can read the backup. Therefore every released schema version needs an explicit, forward migration, a committed Room schema snapshot, and a migration check that starts with the prior schema and verifies representative rows after upgrade.

This is a data-integrity requirement, not just build configuration. Existing expenses, friend records, and split transactions are user-owned history. A PeerSplit feature must be additive until a separately planned, user-confirmed import or conversion exists.

## Step 0 — Capture the current Room v1 contract

**Why:** Before changing a database contract, preserve the exact schema that shipped. Without this baseline, it is not possible to prove that a v1 database can be upgraded, and Room's schema-diff tooling has no trustworthy source version.

**Change:** Enable Room schema export and configure KSP to write snapshots under `app/schemas/`. No table, column, or user-visible behavior changes in this step.

**Evidence:** The command `./gradlew :app:kspDebugKotlin` completed successfully and generated [`1.json`](../../app/schemas/com.just_sri.suvidha.expenses.ExpenseDatabase/1.json). This is build evidence that Room processed the current v1 entities and exported a schema. It is not by itself proof that a future migration preserves rows; the v1 snapshot and migration verification provide that proof.

**Preservation claim:** Existing rows are unaffected by schema export configuration because this step changes compiler metadata only. The migration that follows must use this snapshot as its starting version.

## Migration record template

For every schema migration, add one entry with all fields below:

### Version N -> N+1 — short purpose

- **Status:** Planned / Approved / In progress / Partially implemented / Implemented / Tests passed / Complete.
- **Why required:** State the concrete integrity, compatibility, or feature need. Describe the failure mode without the migration.
- **Schema changes:** List tables, columns, constraints, indexes, and defaults exactly.
- **Data transformation:** State how every old row is preserved or transformed. If a destructive transformation is unavoidable, stop and obtain an explicit product decision before implementing it.
- **Recovery behavior:** Describe the pre-migration backup and how failure is surfaced. Never silently reset the database.
- **Verification:** Run the migration from the exported N schema, seed representative vN data, upgrade to vN+1, and assert all pre-existing values plus new schema constraints. Record the exact command and result. Also record any manual/device validation separately from automated evidence.
- **Evidence limits:** State what was not tested (for example, device restore, very large databases, or rollback from a newer schema).

Every follow-on migration gets its own entry; do not edit old entries to make a later migration appear to have been part of an earlier release.

## Implementation slices

### Version 3 -> 4 — Link local friends and contacts to group identities

- **Status:** Tests passed: migration/link/recovery instrumentation and physical member-picker/restart checks. Final cross-install event-set comparison is a separate pending check.
- **Why required:** The authenticated group identity is a Nostr public key, while friends and phone contacts are local address-book records. An explicit link makes the member list and split picker show familiar names without inferring identity from a phone number, merging existing balances, or publishing contacts to relays. Keeping the mapping in Room makes the user's choice survive restarts and participate in transactional backup/restore.
- **Schema changes:** Add `shared_member_friend_links(memberId TEXT PRIMARY KEY NOT NULL, friendId TEXT NOT NULL, linkedAtMillis INTEGER NOT NULL)` with an index on `friendId` and a foreign key to `friends.id` using `ON DELETE CASCADE`. The public key is global across this phone's groups; multiple independently verified public keys may link to one local friend. No legacy table column or shared-event payload changes.
- **Data transformation:** None. All old expense/friend/split/group/event/outbox rows remain in place; the mapping table starts empty. No existing personal balance becomes a shared group balance automatically.
- **DAO change and reason:** Friend writes use Room `@Upsert` instead of SQLite `INSERT OR REPLACE`. REPLACE deletes the old parent row before inserting its replacement and would trigger the link table's delete cascade during an ordinary friend update. Upsert updates the existing parent row, preserving links. Explicit friend deletion removes only its local links; group identities and immutable ledger history remain.
- **Privacy and recovery:** Links, friend names, phone numbers, and contact IDs remain outside the shared wire envelope. Only explicitly selected contact records become local friends. Backup payload v4 includes the mapping inside the passphrase-encrypted local file; v1/v2/v3 payloads decode with no links. The app's pre-upgrade database copy and non-destructive failure behavior remain in use.
- **Verification plan:** Start from exported schema v3 with seeded personal/shared/outbox rows; migrate to v4 and compare every seeded value. Verify friend updates preserve links, deletion unlinks without deleting ledger events, contact linking reuses an existing friend, invalid linkage rolls back, and backup round-trips linked names. Verify equal and weighted paise allocation, currency precision, and large amounts independently from UI. On the physical phone, check the shared keypad, exact mode, link/unlink, restart persistence, Friends title, and absence of its + action.
- **Evidence limits:** A local friend/contact link is a user-chosen label, not proof that a phone number controls the Nostr key. Invitations still require that member's published KeyPackage and public key. Full-phonebook sync and automatic identity discovery are not implemented.

### Version 1 -> 2 — Additive local group and event tables

- **Status:** Complete; migration and row-preservation test passed.
- **Why required:** Shared groups and immutable actions need durable Room storage. Reusing personal `friends` or `split_transactions` would couple local-only records to group membership and preserve the mutable `isSettled` representation that the shared ledger is replacing.
- **Schema changes:** Add `shared_groups`, `shared_group_members`, and `shared_ledger_events` with group/member keys, group-scoped event ordering, and cascading child cleanup when a group is explicitly deleted. Leave `expenses`, `friends`, and `split_transactions` definitions and rows unchanged.
- **Data transformation:** None. This is additive; the migration creates the new tables and indexes without copying, renaming, updating, or deleting any v1 row.
- **Recovery behavior:** Before Room opens an older database, make a checkpointed copy named for its source and target version. Room then runs the explicit migration. With no matching migration, open fails into the existing recovery UI; destructive fallback has been removed.

### Phase 2 — Manual encrypted local backup and restore

- **Status:** Partially implemented; build and restore verification are pending. Do not call recovery complete until unit/instrumented tests and clean-install restore pass.
- **Why required:** Group history is durable only on one device today. Device loss, reinstall, or accidental data clearing would discard it. A backup must be separate from relay sync, authenticated so tampering cannot turn into a partial ledger, and previewed so importing cannot silently erase current records.
- **File format:** Container version 1 uses a fixed `SUVIDHA1` header, PBKDF2-HMAC-SHA256 at 600,000 iterations, a random 16-byte salt, AES-256-GCM, and a random 12-byte nonce. The complete header is authenticated as GCM additional data. KDF version and work factor are validated before derivation; file and JSON sizes are bounded. Payload version 2 includes current Room v2 expenses, friends, splits, groups, memberships, shared event history, the Nostr identity secret, and each stored MLS state including retained epochs and the sender ratchet. Payload v1 is still decoded as a ledger-only legacy backup.
- **Secret handling:** User-chosen passphrase only; not stored in Room or preferences. UI requires at least 12 characters. Mutable passphrase, derived-key, and plaintext byte buffers are cleared after use where practical. The passphrase is not part of the file.
- **Restore behavior:** The selected file is decrypted and fully decoded/validated first, including group event replay. The UI presents creation time and record counts, followed by explicit confirmation. Replacing rows occurs inside a Room transaction and abort-on-conflict inserts; validation/insert failures roll back the old data.
- **Recovery boundary:** The file now carries the local Nostr identity secret and Marmot MLS group states, then re-wraps them to this device's Android Keystore on restore. The current snapshot does not include Marmot KeyPackage bundles, cached messages, or pending publish obligations, so outstanding invitations and pending relay work are not promised to recover. Cross-device and clean-install restores remain unverified. Google Drive remains a separate, later adapter.
- **Schema changes:** No Room schema version change in this slice. The file container and payload have independent version fields so portable backup evolution does not require pretending the on-device schema changed.
- **Verification:** `./gradlew :app:assembleDeviceTestDebug :app:testDeviceTestDebugUnitTest :app:compileDeviceTestDebugAndroidTestKotlin :app:assembleDeviceTestDebugAndroidTest` passed. The four instrumented tests ran on the attached OnePlus CPH2869 as `com.just_sri.suvidha.expenses.peersplitpreview.test`, result `OK (4 tests)`. They cover MLS group state + retained epoch + sender ratchet recovery, backup JSON/transaction replacement, v1→v2 row preservation, and shared-event replay/deduplication. Manual launch and UI group creation also succeeded in the separately named preview app. A clean-install encrypted backup export/import including actual Keystore/MLS files has not yet been exercised end-to-end.
- **Evidence limits:** Large (near-limit) backups, interrupted external-document writes, cross-version restore, and recovery after identity state is introduced remain unverified.

### Phase 3 — Local Nostr identity, encrypted MLS state, and group creation UI

- **Status:** Partially implemented; local identity, encrypted group state, and group creation are implemented and verified on a physical device. Invitations and membership lifecycle remain planned.
- **Why required:** Relay membership cannot be authenticated with a display name or a random local ID. Nostr provides a stable secp256k1 signing identity; MLS maintains group epochs and sender ratchets. Storing MLS state unencrypted, or losing a sender-ratchet write after message encryption, can expose long-term secrets or repeat an AEAD key/nonce pair.
- **Changes:** Added a Compose group list/create/detail flow. Group creation generates a 32-byte Nostr group ID, creates a Quartz secp256k1 identity (persisted under an Android Keystore AES-GCM wrapping key), calls Marmot to create a local one-member MLS group, and records the identity public key as the owner. Added an encrypted local `MlsGroupStateStore`; it encrypts group state, retained epoch secrets, and the sender ratchet, authenticates the Nostr group ID as AAD, and fsyncs each ratchet update before return. Backup payload v2 exports those secrets only inside the passphrase-encrypted container.
- **Schema changes:** None. Key files and MLS state are app-private, excluded from Android automatic backup, and are recoverable only through the explicit encrypted export.
- **Verification:** `:app:assembleDeviceTestDebug`, local unit tests, Android-test Kotlin compilation, and Android-test APK assembly passed. The current device instrumentation suite passed `OK (4 tests)` on the attached OnePlus CPH2869. The separately named preview package `com.just_sri.suvidha.expenses.peersplitpreview` installed beside the existing app, launched without a fatal exception, and created a test group through the UI; Marmot state persisted and the group appeared after creation. MLS state and recovery-export tests cover retained epoch and sender-ratchet persistence. Required next checks: durable KeyPackage/publish-obligation recovery, invite/join on a second identity, and member-removal/epoch-exclusion tests.
- **Not implemented in this slice:** Invite sending and relay synchronization are implemented in Phase 4. Invite acceptance into SUVIDHA's Room group list, KeyPackage recovery, membership removal/rotation UI, multi-relay retry/outbox, and sync convergence remain planned.

### Phase 4 — Manual Nostr relay sync MVP

- **Status:** Partially implemented; manual sync and outbound invites are wired to Marmot and run on a physical device. Inter-device invitation acceptance and ledger convergence remain unverified.
- **Why required:** A group on one phone cannot become multi-device without transporting authenticated protocol events. Relays are untrusted mailboxes: verify NIP-01 IDs/signatures before processing, decrypt/validate with Marmot/MLS, and do not make the remote service a source of ledger truth.
- **Changes:** Added a manual “Sync now” action. It queries two configured public Nostr WebSocket relays for bounded kind-445 group events and kind-1059 inbox gift wraps, verifies outer event hashes and Schnorr signatures, opens gift-wrap/seal layers with the local Nostr signer, checks seal signature and rumor-author binding, then passes group events/Welcome events to Marmot for MLS verification and epoch processing. Added “My Nostr key” to display/copy the app-generated public key and publish a signed Marmot KeyPackage from SUVIDHA. The private MLS KeyPackage bundle is saved encrypted with a separate Android Keystore AES-GCM key so the app can later process a Welcome. Added an “Invite member” action that looks up a signed Marmot KeyPackage event for a 64-character Nostr public key, then uses Marmot to add the member and deliver the encrypted Welcome. The invited member is added to the local roster after the Marmot operation succeeds. The Marmot publisher adapter waits for positive Nostr `OK` responses before it reports success. Group metadata carries the two relay hints. UI reports partial relay results and keeps local use available if relays fail.
- **Privacy and integrity boundary:** Relays can observe the client's IP, connection times, event sizes, event kinds, and routing tags including group IDs/recipient pubkeys. Transaction payloads are not yet sent through this path. Do not call this “zero knowledge” or claim ledger replication.
- **No Room migration:** The first sync slice uses the existing Marmot encrypted files and current Room group IDs; it does not create an outbox or cursor table, so no database version bump is justified yet.
- **Limitations:** Sync is user-triggered and foreground only. It fetches a bounded recent set (up to 2,000 group events and 500 inbox gift wraps per relay) with no durable cursor, gap repair, event backlog paging, or WorkManager retry. Invitees must have already published a compatible KeyPackage on a configured relay. Recipient-side Welcome processing does not yet add the joined group to SUVIDHA's Room group list, so a two-SUVIDHA join flow is not complete. KeyPackage bundles and pending publish obligations are not included in the recovery file. Removal/revocation is not implemented.
